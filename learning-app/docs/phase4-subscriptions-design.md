## Recommended first release

### Private Company Test Mode-only learner checkout

Company Test Mode-only courses remain hidden from Explore and public subscription offers. A recorded Test Mode plan can be tested through the private dashboard route shown to the instructor, but only after the exact learner email is listed in the server-only GROWVELT_LEARNING_SUBSCRIPTION_TEST_LEARNER_EMAILS variable. Keep this allowlist empty outside a controlled Test Mode environment. The matching additive migration must be applied before the route is deployed. This private test path does not authorize Live checkout.

- For the first release, offer an opt-in subscription to one instructor's catalog, not an unlimited Growvelt-wide marketplace pool. Provider-organization courses are excluded until organization payee and payout attribution are supported for subscription revenue. This keeps the seller/payee identifiable and avoids inventing a cross-instructor revenue-pool formula.
- Keep one-time course purchases available and unchanged. Subscribing does not convert, cancel, or re-price an existing purchase; a course already owned by the learner is not charged again for access.
- Start with one NGN monthly plan per seller and a fixed, seller-visible course list. Do not include company workspaces, company seat billing, coupons, free trials, featured-placement fees, or cross-seller bundles in v1. Phase 3C's accepted per-employee/per-paid-course model remains unchanged.
- Snapshot the plan, included course IDs, seller/payee, commercial-terms version, price, platform share, and seller share for each billing period. Use a subscription-specific ledger source; do not disguise recurring invoices as ordinary single-course learner orders.
- Grant or extend access only after trusted server-side payment confirmation. Cancellation stops future renewal but retains access through the paid-through date. A failed or unverified renewal never extends access. No implicit grace period in the first release; communicate the expiry date and provide a clear recovery path.
- Seller proceeds follow the existing hold and admin-review controls. No automatic seller transfer is part of subscriptions.

## Paystack constraints to account for

Paystack's current subscription documentation says subscriptions use cards and Nigerian Direct Debit, require a plan and customer authorization, and send lifecycle/payment events that the application must process. Its docs also say failed subscription charges are not retried. This means v1 needs explicit failed-payment and access-expiry handling; it cannot assume retries will restore service. See [Paystack Subscriptions](https://paystack.com/docs/payments/subscriptions/) and [Subscription API](https://paystack.com/docs/api/subscription/).

## Live-subscription accounting migration applied; app release still pending

The migrations `20261128000000_add_subscription_invoice_earnings_source.sql` and `20261129000000_add_live_subscription_refund_reversal.sql` add an invoice source to commercial allocations and ledger transactions, permit Live-domain subscription records, preserve paid-period course-access rules, and record a verified Live invoice's instructor share as held. A database trigger rejects attempts to mark invoice-backed earnings available, reserved, paid, or recoverable outside the invoice-specific refund/release safeguards. Both migrations were applied to the verified hosted Growvelt Courses project on 2 November 2026, after a CLI dry run showed exactly these two pending migrations. A subsequent dry run confirmed the remote database is up to date; vault settings were skipped.

The local Phase 4 refund slice now adds a separate invoice-level admin view and two server routes; it does not change course-order refunds. Refund initiation requires same-origin admin authentication, Live Paystack configuration, both the existing global refund switch and the separate subscription-refund switch, a paid Live NGN invoice, exact confirmation of the invoice reference, matching provider transaction verification, and an empty provider refund history. A database claim is acquired before the provider request. The provider merchant note includes the local refund-case ID so a timed-out request can only be recovered by the exact Live transaction, full amount, and unique case marker. Recovery is read-only: it never posts another refund, waits 15 minutes when the provider ID was not recorded, and leaves ambiguous or absent evidence for manual review. Only a separately fetched, exact `processed` provider refund can reverse the invoice allocation, ledger the refund, mark that invoice refunded, and withdraw access provided solely by that invoice period; independent one-time-purchase access and learning history remain intact.

The Payment Operations subscription list and event history use service-role-only admin RPCs; the database test now verifies email search, scoped timeline data, and denial to anonymous, authenticated learner, and instructor roles. A failed provider refund is not offered as a fresh retry in the UI. Refund-request and attention emails use the learner's first name, and the request notice is sent before the provider call so a funding rejection does not silently omit the initial case notice.
